# 154/123 双站小时级容灾设计

## 目标与边界

默认由 154 提供霓虹酒馆服务；154 故障时，123 可接管同一套业务数据。两站按小时同步可恢复副本。用户已授权继续准备和验证生产部署；所有线上写操作仍须先完成只读盘点、备份和目标服务隔离，且不得影响原有无关项目。切流前必须通过本设计列明的 TLS、数据完整性、同意门禁和回退验收。

“两站都能做主站”在本设计中表示两台机器均可被提升为主站，但任何时刻只能有一台主写。另一台是可提升的热备，不采用双写。复制按计划每小时完成时，故障恢复点目标（RPO）约一小时；如果复制失败或积压，实际 RPO 会继续扩大，系统必须显示距最后一次成功复制的时间/积压并告警，不能继续声称满足一小时 RPO。故障时未到下一同步点的数据可能丢失。

本设计是新的可用性子系统，与总站跨站治理、私聊审核、素材市场和签名更新分开。全局管理权仍以 154 为默认控制面；容灾租约只决定业务数据库哪一侧可写，不转移全局管理员权限或签名密钥。

## 已确认的产品选择

- 默认主站：154；候选接管站：123。
- 数据副本间隔：每 1 小时。
- 接管方式：独立仲裁服务确认旧租约失效后，授予新主站租约；旧节点租约到期后必须拒绝写请求。
- 线上环境：已获授权进行隔离部署准备和验证；实际切流以 TLS、数据核对及回退演练通过为前置条件。
- 浏览器当前按 IP 访问：切换到另一个 IP 后需要重新登录。已有页面可检测主站状态并切换 API/页面地址；新访客在 154 整站不可达时，不能依赖 154 页面里的 JavaScript 自动跳转，须提供备用地址。无域名情况下不承诺冷启动无感切换。

## 组件

1. **霓虹酒馆节点**：两台应用使用相同兼容版本、迁移版本及解密用户加密设置所需的受控密钥。所有会改变业务数据的 HTTP 请求都要先通过本地租约校验；无有效写租约时以只读/服务不可用方式失败关闭。静态资源、健康检查和状态查询可在热备上读取。
2. **独立仲裁器（witness）**：部署在与两台业务节点故障域独立的位置，不存储账号、对话、角色卡、世界书或模型 API 密钥。保存当前持有者、递增 epoch、租约到期时间和最小审计元数据；只通过 HTTPS 接受节点身份签名请求，签发短时、绑定节点及 epoch 的租约。
3. **小时同步任务**：只从当前有效写主站向已确认只读的热备传输一致性快照。活动主站翻转后传输方向随新租约改变。
4. **浏览器故障切换器**：以不携带会话凭据的方式探测本站和备用站状态 API。各站后端通过私有 CA 校验的 HTTPS 查询 witness；浏览器仅在备用站报告已验证的更高 epoch 主写租约后切换。仅客户端单次连接失败不足以触发写端切换。

## 租约与防止双写

- 仲裁器每次主站任期递增 `epoch`。租约只可由一个节点持有，默认有效期 60 秒、每 15 秒续租；节点使用可信系统时钟，要求最大偏差不超过 2 秒。偏差超限、租约过期、签名错误或无法确认仲裁状态时，节点停止接受写操作。
- 仲裁器仅在旧租约到期并经过时钟偏差保护窗口后才签发新 epoch。旧 epoch 永远不能续期或重新生效。
- 租约门禁不能只放在 HTTP 入口：所有数据库写事务必须在开始时验证当前 epoch/租约，并在提交前再次验证；若剩余有效期不足 10 秒或无法确认任期则拒绝开始写入。单个写临界区最长 10 秒，AI 网络请求不得放在数据库写事务内。
- 上传文件先写入当前节点私有暂存区，校验完成后必须持有有效租约才能原子提升为正式文件；租约失效时清理或隔离暂存文件，不得留下数据库引用与文件状态不一致。
- 热备数据库以 SQLite query-only/只读文件权限打开，媒体目录只读挂载；应用层门禁之外再由操作系统权限阻止误写。提升为主站时先取得新 epoch，再切换数据库和媒体目录的写权限。
- 写入门禁覆盖登录会话更新、注册、角色卡/世界书修改、聊天和生成结果、管理员操作、素材发布及处置 API，也覆盖生成/定时/同步 worker、管理命令和启动任务；遗漏路径由测试枚举 Django 非安全 HTTP 方法路由及后台任务入口并验证。
- witness 不可达时，不授予新主站。已签发租约只可用至其到期；此后两节点均拒绝写入，宁可暂时不可用，也不允许分叉写入。
- 每个写请求仅凭本节点缓存的、未过期且签名正确的租约校验；节点重启不得延长旧租约。

## 每小时数据同步

- 数据源始终是当前有效写主站；同步前要求接收端持有者确认其处于备用状态且没有有效写租约。为使数据库与上传文件属于同一恢复点，源站短暂暂停新写入并排空在途数据库事务/文件提升，再生成 SQLite 与媒体清单快照；若无法在配置的维护窗口内完成，取消本轮快照并保留旧副本，不以不一致快照继续。
- 使用 SQLite Online Backup API 产生一致性数据库快照，不复制正在使用的 `db.sqlite3` 文件。同步包包含 SQLite 快照、`MEDIA_ROOT` 中的用户上传文件、应用版本、数据库迁移版本、`epoch`、创建时间和 SHA-256 清单。
- 快照在独立临时目录生成；执行 `PRAGMA integrity_check`、迁移版本检查、文件数量/摘要核验后，使用 HTTPS 节点身份签名传输，并以单独的复制加密密钥加密。复制密钥不进入数据库、仓库或日志。
- 接收端先存为暂存快照，重新验证签名、摘要、版本和 SQLite 完整性；校验失败时保留上一份可用快照并报警，绝不覆盖。
- 安装已验证快照前只停止热备上的霓虹酒馆应用服务；使用原子目录/文件切换后再启动并执行健康检查。只可操作明确命名的霓虹酒馆服务，不接触 Nginx 或无关进程。
- 默认保留最近 24 份按小时验证通过的快照；清理仅作用于本系统备份目录，先确保至少一份可恢复快照存在。
- 若当前主站为 123，恢复后的 154 必须从 123 接收新快照；不得把旧 154 快照反向覆盖 123。

## 故障接管、浏览器和恢复回切

1. 浏览器探测到 154 超时后查询 123 的状态 API；154 可达时也查询本站状态 API。浏览器不直接连接 witness，也不因单个请求失败自行更改写目标。
2. 若 123 的状态 API 尚未确认它持有更高 epoch 的有效主写租约，浏览器显示连接/仲裁异常并有限重试；不向 123 发送写请求。
3. 只有 123 后端通过 witness 验证并保存新 epoch 后，其状态 API 才报告 `primary`。浏览器核对节点 ID 和更高 epoch 后切换到 123。因两个 IP 的 host-only Cookie 不共享，页面清楚提示重新登录，不尝试复制或窃取浏览器会话。
4. 154 恢复时先保持无写权限。比较任期、数据库/媒体清单和迁移版本；从当前主站 123 同步完整快照至 154，校验并通过健康检查后，witness 才可执行有审计的受控回切。
5. 若回切或快照恢复失败，继续让已验证的当前主站服务；旧节点维持只读/隔离，不自动降级或回滚到更旧数据。
6. witness 故障、网络分区、时钟漂移或两节点状态不一致时停止自动提升，展示明确状态和人工恢复指引。

## 登录与隐私

- 主站数据库快照包含账号密码哈希、Django 会话数据和用户业务数据；原始密码不会传输。热备能服务接管意味着其受信任边界可读取同一业务数据库，必须按完整生产数据保护。
- 站点私聊镜像与容灾数据库副本是两个不同用途。同步副本不得被误计为审核镜像；管理界面区分副本健康与内容审核状态。
- 注册/登录页隐私告知须说明账号及业务数据会加密复制到 123 作为灾备副本、同步周期约一小时、故障时可能损失最近未同步内容、恢复期间可能要求重新登录及获准访问角色。未完成告知版本更新和同意前，不允许启用生产复制。
- HTTPS 证书校验失败、节点签名无效或复制密钥缺失时拒绝同步，不降级明文。审计只记录任期、节点、摘要、结果和错误代码，不记录凭据或完整用户内容。

## 隔离测试方案

测试完全在本地临时目录中运行：两份独立 SQLite 数据库、两份临时媒体目录、三个进程/测试夹具模拟 154、123 和 witness。生成合成账号、会话、角色卡、世界书、聊天与上传文件；禁止读取当前开发数据库中的真实用户内容。

验收覆盖：

- 154 主写、123 只读；失去仲裁后租约过期，两边均无法写。
- witness 授予新 epoch 后仅 123 可写；旧 154 继续运行或网络分区时仍被写入中间件拒绝。
- 小时任务生成一致性快照；数据库与媒体文件在目标端摘要匹配，中文、UUID、权限关联、会话和文件内容完整。
- 传输中断、损坏摘要、错误密钥、未知版本、迁移不匹配、磁盘不足、SQLite 校验失败和服务启动失败均不替换最后一份可用快照。
- 154 失效后在 123 写入新数据；154 恢复后只从 123 回同步，完成校验后才允许回切；不能以旧快照覆盖新数据。
- 浏览器探测单点超时但 witness 仍指向 154 时不切换写入目标；租约转移确认后切换并提示重新登录。
- 访问审计、告知同意、复制保留策略、租约续期及服务隔离都有自动化测试；全套后端/前端测试和迁移检查通过。

## 生产变更保护边界

- 任何线上写操作前先只读检查目标路径、服务、端口、代理、防火墙和备份状态；不得覆盖、删除、停止或重启无关项目。
- 修改共享 Web 配置前必须备份并执行语法检查，只允许 reload；优先使用隔离目录、独立端口和明确命名的霓虹酒馆服务。
- 生产数据复制只允许在隐私告知/同意门禁启用、双方版本和加密密钥核对后执行；不得复制模型 API 密钥或服务器凭据。首次快照前必须备份并核对来源/目标记录数和摘要。
- 未完成业务站点公网 HTTPS、见证 TLS 验证、初始快照核验、登录/聊天检查和回退演练前，不启用写主站自动切换，不宣称生产容灾已启用。

## 需要实现计划覆盖的模块

- 仲裁器协议、签名 epoch/租约及失效测试。
- Django 写请求租约门禁和只读热备健康状态。
- SQLite 一致性快照、媒体快照、加密传输、摘要验证和原子恢复。
- 浏览器多节点状态探测、主站切换和重新登录提示。
- 版本化隐私告知、同意门禁、隔离部署样例和中文运维说明。
- 本地故障注入与恢复回切测试；线上暂存/部署另列阶段，不与本地验收混为一谈。

## 无公网证书的 Witness 接入调整（2026-09-25）

挂机宝 witness 使用固定 NAT 端口，当前没有该子域名的 DNS 修改权限，无法为高位公网映射端口完成公开 CA 的 HTTP-01/TLS-ALPN-01 验证。不得因此退回明文或让浏览器忽略证书错误。采用专用私有 CA 保护节点到 witness 的 HTTPS：根签名私钥只在受控离线环境保存，witness 仅持有带 `hbe3.wch1.top` SAN 的叶证书及私钥；154、123 只安装 CA 公共证书，并在 witness 专用 HTTP 客户端中显式信任该 CA。证书校验失败、域名不匹配或证书过期时必须失败关闭，禁止全局关闭 TLS 校验或回退 HTTP。

浏览器不再直接请求 witness。页面以不携带会话凭据的方式查询本站及配置的备用站 `/api/disaster-recovery/status/`。状态响应只包含公开的节点 ID、角色、epoch、租约有效期和复制健康信息，不包含用户数据、密钥或会话。跨源备用站状态查询仅允许精确配置的站点来源，且始终省略 Cookie。备用站 API 只在其本机验证到 witness 签发且仍有效的更高 epoch 租约后报告 `primary`；前端仅在备用节点 ID 匹配、角色为 `primary` 且 epoch 严格高于本机观察值时跳转。任一状态接口超时、CORS 不匹配、租约缺失/过期或 TLS 校验失败时均不跳转。

该方案解决 witness 的私有服务证书，不替代用户浏览器到业务站点的公网 HTTPS。123 的现有 HTTPS 必须先通过实测；154 当前没有 443 监听，必须另行配置并验证受信任的公网 HTTPS，才能把完整双站容灾称为安全可用。NAT 的高位公网端口映射到 witness 内网 443 即可；若映射端口稳定，witness 无须控制域名 DNS，也无须为其开放公网 80。生产启用仍须先备份、部署同版应用、初始化一致性快照并完成受控切换演练。
